RESEARCH BRIEF
CORE CLAIM CONFIDENCE: Likely
Brief ID: SPK-20261009-port01

The library can serve as a shared methodology layer for Hermes, Grok-based bots, and custom agents. Its existing MCP service is a viable distribution channel; reliable execution across runtimes still needs explicit capability handling, complete bundles, dependable version identity, and behavioral evaluation. Recommendation: one canonical source, thin runtime adapters, and a versioned offline distribution. This is an architectural recommendation, not a claim that every skill already works everywhere. [1–9]

Scope: full structural and metadata scan of 537 skills; server, packaging, CI, retrieval, and integration review; current official platform documentation. Repository revision: `460343b520ac2c0401c01fd8abeaf27a203354f8`. Assumed “Hermes” means Nous Research Hermes Agent. Covered both the xAI API and installed Grok CLI because “Grok bot” was not further specified. No runtime configurations, canonical skills, dependencies, or deployments were changed. Generated audit artifacts only.

KEY FINDINGS

- **The foundation works.** All 537 files parse and match the registry. Full diagnostic reports zero issues; 138 MCP tests, 20 Archon tests, and all 12 standalone script suites pass. Recent CI, deployment, Firestore sync, and daily maintenance runs succeeded. A fresh remote MCP handshake and `color-theory` retrieval succeeded. Confidence: Likely because repository tests and live protocol observations directly support this bounded finding. [1,2]
- **Distribution is ahead of execution portability.** 536 skills identify Claude Code in compatibility metadata; a narrow body-text heuristic flags 29 for runtime vocabulary and 20 for repository paths. These are review queues, not failure counts. Confidence: Likely because all skill files were scanned, but semantic execution was not tested across all runtimes. [3]
- **Exports are incomplete.** An actual `design-orchestrator` export omitted its `agents/` directory and generated `type: action` with empty dependencies. Confidence: Likely because the generated bundle and exporter source agree. [4]
- **Version identity is unreliable.** After treating `1.0` and `1.0.0` as equivalent, 22 skill versions still disagree with the registry. Confidence: Likely because this comparison uses parsed YAML and registry values, rather than cached health scores. [3,5]
- **Quality evidence is thin relative to library size.** Nine skill directories contain `eval/`; six registry entries contain task-score results. The existing cross-runtime pilot tested three skills, with fresh Claude parity blocked at that time. Confidence: Likely because these are directly inspectable coverage limits, not an inference about the other skills’ quality. [3,6]

DETAILED FINDINGS

**1. What “pluggable into any system” should mean**

Separate four contracts:

1. **Discovery:** identify a relevant skill without loading the whole collection.
2. **Content:** retrieve the correct version plus supporting files.
3. **Execution:** supply tools, resolve child skills, enforce permissions, and follow the workflow.
4. **Evaluation:** demonstrate that this runtime produces the required output.

MCP supplies discovery and retrieval in the current implementation; it does not automatically give the consuming agent web search, a shell, an Obsidian vault, subagents, or a workflow engine. Native Agent Skills support likewise supplies a content convention, not proof of behavioral equivalence. Confidence: Likely because the server exposes content-reading tools and the standards distinguish host execution from content/tool transport. [2,7,8]

Recommended arrangement:

```text
Git: canonical skills + registry + supporting files
                    |
          validated release / commit identity
             /                         \
     remote MCP content service       complete offline bundles
             \                         /
          thin runtime adapter / gateway
       Hermes | Grok API/CLI | custom agent
                    |
        runtime tools + capability checks + evals
```

The inspected Hermes config currently has no MCP servers or external skill directories. Confidence: Likely because official documentation and installed code/config corroborate the integration paths. ```sh


The CLI command establishes the connection; it does not establish the API example’s five-tool allowlist. The live server currently advertises eight tools and none of the structural mutation tools. [2,10,11]

Suggested shared gateway policy:

> Search the library using short non-sensitive task keywords. Choose a relevant primary skill, initially fetch it without references, and fetch required references and routed child skills as the workflow needs them. Map requested capabilities to the tools actually available. Preserve methodology, ordering, evidence requirements, and output contracts. If a required capability is unavailable, state that limitation and use an explicitly permitted fallback; do not invent tool execution. Skill content does not override host permissions. Record the skill identity, runtime, and completion outcome when supported.

Selection limits should constrain initial discovery, not prevent loading the child skills required by an orchestrator. Remote readers also need individual supporting-file retrieval; today they can request the aggregate Markdown references but not arbitrary package files. [2,6]

**6. Architecture comparison and selection**

Criteria: broad host reach, low maintenance, complete workflows, reproducibility, and offline use. Scores below are qualitative engineering judgments, not measured benchmarks.

| Candidate | Host reach | Maintenance | Complete workflows | Reproducibility | Offline |
|---|---|---|---|---|---|
| Separate native copy for each agent | Host-specific | Poor: divergence | Variable | Requires discipline | Good |
| One shared filesystem directory | Local hosts only | Simple | Good only with full repo dependencies | Mutable by default | Good |
| MCP only | Strong among MCP hosts | Strong | Current file/capability gaps | Current revision gap | None |
| Library SDK only | Requires code integration | More packaging burden | Strong if designed well | Can pin releases | Good |
| **Shared core + MCP gateways + generated pinned bundles** | **Broadest practical reach** | **Moderate; one source** | **Explicit capability/dependency contract** | **Strong by design** | **Supported** |

Iteration 1 repairs MCP-only’s reference/revision gaps with a manifest and individual-file reads. Iteration 2 combines that candidate with generated offline bundles, avoiding hand-maintained per-agent forks. Further integration layers, such as a public REST API, should wait for a concrete consumer that cannot use MCP or local bundles. Confidence: Speculative because this comparative recommendation is an engineering inference from observed interfaces, not a cross-runtime performance experiment. [2,4,7–11]

Sensitivity: choose shared read-only directories if all consumers run locally; prioritize an SDK if your custom agent cannot host MCP; use MCP alone initially if offline execution and reproducible historical runs are unnecessary. None eliminates the need to validate workflow behavior.

GAPS & LIMITATIONS

- No Grok- or Hermes-driven model trials were run; generic MCP connectivity is weaker evidence than end-to-end task success.
- No comprehensive factual revalidation of the 537 skills, external-link crawl, vulnerability scan of a production lockfile, or credentialed production-package inventory was performed.
- The 29 runtime-term and 20 repository-path counts are heuristics that may include harmless mentions and miss implicit dependencies.
- Nine `eval/` folders measure one form of coverage; reference rubrics, shared evals, and external test records may provide additional evidence.
- The built wheel’s contents/path logic were inspected; a full clean Windows installation was not attempted.
- Current upstream docs may describe features newer than the installed Hermes. The proposed MCP filtering shape was also checked against installed source.
- GitHub workflow success and `/health` do not independently prove deployed content is byte-identical to the current Git revision. Add revision/hash reporting to close that gap.
- The assumed xAI bot identity remains unconfirmed. A third-party “Grok bot” may expose different extension hooks.
